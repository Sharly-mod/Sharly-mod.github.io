## Ce que j’observe

Les outils d’IA générative sont devenus une partie normale du travail de
développement : génération de squelettes, explication d’une erreur, écriture de
tests, reformulation d’une documentation. Sur un projet étudiant, ils peuvent
faire gagner un temps réel, surtout sur le code répétitif.

Mais ils changent la nature de l’effort. On passe moins de temps à écrire et
plus de temps à **vérifier, comprendre et intégrer**. Ce déplacement est
souvent sous-estimé.

## Les risques que je retiens

- **Le code non compris.** Un extrait qui « marche » peut être incohérent avec
  l’architecture du projet, mal nommé ou impossible à maintenir.
- **Les dépendances fantômes.** Un assistant peut proposer un paquet qui
  n’existe pas, ou une version obsolète. C’est un vecteur direct de supply
  chain.
- **Les secrets dans les prompts.** Une clé API collée dans une conversation
  est une fuite. Les outils sérieux ont des modes de confidentialité, mais la
  première règle reste de ne pas envoyer de secret.
- **La dette de revue.** Générer 300 lignes en 30 secondes ne dispense pas de
  les relire. Au contraire : plus le code arrive vite, plus la revue doit être
  structurée.
- **La propriété intellectuelle.** Tous les extraits ne sont pas
  réutilisables selon la licence du projet. C’est un sujet à connaître, même
  en BTS.

## Ma méthode

1. **Un prompt sans secret** : jamais de mot de passe, de token ou de donnée
   personnelle.
2. **Une demande cadrée** : langage, version, contraintes, style du projet.
3. **Une revue ligne par ligne** : je dois pouvoir expliquer chaque instruction
   devant le jury.
4. **Des tests** : si je ne sais pas tester le code généré, je ne le merge pas.
5. **Une documentation** : noter ce qui a été généré et pourquoi, pour ne pas
   laisser une boîte noire dans le dépôt.

## Le lien avec la supply chain

L’IA accentue le problème de la confiance dans les dépendances : elle peut
suggérer un paquet, une commande ou une configuration sans que l’on connaisse
sa provenance. La vérification humaine n’est pas un frein à la productivité,
c’est la condition pour que le gain de temps ne devienne pas une dette de
sécurité.

## Ce que je retiens pour l’oral

L’IA ne remplace ni la compréhension du besoin, ni la revue, ni les tests. Un
développeur SLAM doit savoir **expliquer** ce qu’il livre. C’est exactement ce
que le jury évalue : pas la vitesse de frappe, mais la capacité à justifier un
choix technique.
